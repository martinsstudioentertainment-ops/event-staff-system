1. Database impact

Proposed additive schema only. No changes to submit.php validation outcomes. Existing tables staff, staff_registrations, staff_blacklist remain authoritative for registration state.

1.1 New tables (proposed)

registration_fraud_assessments — one row per successful submit batch

Written after saveRegistrations() succeeds. Links to first inserted staff_registrations.id and staff.id.

registration_fraud_assessments
  id                  INT UNSIGNED PK AI
  staff_id            INT UNSIGNED NULL      -- FK staff.id
  registration_id     INT UNSIGNED NULL      -- FK staff_registrations.id (primary row)
  email               VARCHAR(150) NOT NULL  -- denormalised for queue sort
  risk_score          TINYINT UNSIGNED       -- 0-100
  risk_tier           ENUM('low','medium','high')
  mode                ENUM('shadow')         -- always shadow in Phase F
  flags_json          JSON NOT NULL          -- array of flag codes + metadata
  duplicate_matches_json JSON NULL           -- matched staff_ids + match types
  queue_status        ENUM('open','reviewed_ok','escalated','dismissed') DEFAULT 'open'
  reviewed_by         INT UNSIGNED NULL      -- admin_users.id
  reviewed_at         TIMESTAMP NULL
  review_note         TEXT NULL
  created_at          TIMESTAMP DEFAULT CURRENT_TIMESTAMP
  INDEX idx_fraud_queue (queue_status, risk_tier, created_at)
  INDEX idx_fraud_staff (staff_id)
  INDEX idx_fraud_email (email)
  INDEX idx_fraud_score (risk_score)

registration_identity_index — normalised lookup keys (shadow duplicate detection)

Supports cross-email matching without scanning full staff table on every submit. Populated/updated post-save from existing staff row.

registration_identity_index
  id                  INT UNSIGNED PK AI
  staff_id            INT UNSIGNED NOT NULL
  key_type            ENUM('pps_norm','psa_norm','iban_norm','mobile_e164','identity_composite')
  key_value           VARCHAR(128) NOT NULL   -- normalised or HMAC hash for IBAN
  key_display_hint    VARCHAR(32) NULL          -- e.g. IBAN last 4, never full IBAN in logs
  updated_at          TIMESTAMP
  UNIQUE KEY uq_identity_key (key_type, key_value)
  INDEX idx_identity_staff (staff_id)

fraud_velocity_buckets

2.3 Retention policy (architecture)

  • Assessments + meta: 24 months, then anonymise email/IP (retain aggregate stats)
  • Identity index: lives with staff record lifecycle
  • Velocity buckets: rolling windows only (24h / 7d / 30d) — auto-prune
  • Review audit: 36 months (align with admin_audit_log)

3.2 Admin Fraud Queue

  • List query: paginated WHERE queue_status='open' ORDER BY risk_score DESC — <50 ms at 10k rows with indexes
  • Detail view: 1 assessment + meta + matched staff JOINs — <30 ms
  • No impact on public registration pages when flag OFF

3.3 Cron (fraud-velocity-scan.php)

  • Nightly aggregation over last 24h/7d — estimated <2 s at 10k assessments
  • Ops email only if high-risk open count > configurable threshold (default 5)

3.4 Risk mitigations

  • Post-commit hook only — never inside registration transaction
  • Flag OFF = zero queries (same as today)
  • Identity index avoids full-table scan on staff
  • Peak load: queue writes batched; consider register_shutdown_function for assess

4.2 Data NOT collected in Phase F

  • Full browser fingerprint canvas/WebGL (unless F4 approved with DPIA)
  • Third-party fraud SaaS scores passed to applicant
  • Automated credit checks or government ID verification
  • Sharing fraud scores with event organisers or contractors

4.3 Data minimisation

  • IBAN stored in index as HMAC-SHA256 (server secret) — queue shows last 4 only
  • PPS stored as normalised uppercase — admin queue masks middle digits
  • PSA stored normalised — display full licence to admin only (already in staff record)
  • IP truncated to /24 for displays after 90 days (optional anonymisation job)

5. GDPR considerations

Olasentra operates in Ireland/EU. Phase F processes personal data already collected at registration; it adds security/fraud monitoring metadata.

5.1 Lawful basis

ProcessingBasisRationale
Registration + payroll fieldsContract / Legitimate interestExisting — connecting staff to opportunities
Fraud assessment (shadow)Legitimate interest (Art 6(1)(f))Protect platform integrity, organisers, genuine applicants
IP + device metadataLegitimate interestSecurity monitoring; balanced against applicant rights
Admin manual reviewLegitimate interestHuman decision — no automated rejection (Art 22 safe)

5.2 Data subject rights

  • Access: Fraud assessment rows for their email/staff_id included in SAR export (admin tool)
  • Rectification: Correcting staff profile updates identity index on next save
  • Erasure: Staff delete flow must cascade or anonymise fraud assessments (architecture requirement)
  • Object: Document process for fraud-metadata objection (likely upheld only where no active registrations)

5.3 Automated decision-making (Art 22)

Phase F produces risk scores for admin review only. No legal or similarly significant effect on applicants. Scores do not change registration outcome. This architecture intentionally avoids Art 22 automated decision scope.

5.4 DPIA recommendation

Lightweight DPIA advised before enabling shadow mode in production:

  • Document necessity of IP/device retention vs alternatives
  • False-positive impact assessment (legitimate applicant flagged — still registered)
  • Retention schedule sign-off
  • Processor list if IP intelligence API added (F4)
  • Privacy Notice update: “We monitor registrations for fraud and duplicate identity to protect the platform”

5.5 Cross-border

  • Data remains on existing Namecheap/cPanel hosting (confirm region in DPIA)
  • IP geo lookup: prefer self-hosted MaxMind or EU-hosted API; document sub-processor

6. Admin review workflow

6.1 Principles

  • Every flagged application already succeeded as a registration — review is post-hoc
  • Admin actions are informational unless operator explicitly uses existing tools (reject registration, blacklist)
  • Queue default sort: High risk → newest first
  • No applicant notification when flagged (avoid tipping off fraudsters)

6.2 State machine

[submit.php success] │ ▼ ┌───────────────────┐ │ Shadow assess │ risk_score + flags (always runs if flag=1) │ queue_status=open │ if tier=low AND no compliance flags → optional auto-dismiss* └─────────┬─────────┘ │ ▼ ┌───────────────────┐ Admin: Mark OK ┌─────────────────┐ │ OPEN (in queue) │ ────────────────────────► │ reviewed_ok │ └─────────┬─────────┘ └─────────────────┘ │ │ Admin: Escalate ▼ ┌───────────────────┐ Admin: Dismiss ┌─────────────────┐ │ escalated │ ────────────────────────► │ dismissed │ └─────────┬─────────┘ (false positive) └─────────────────┘ │ │ Admin manual only (existing tools): ▼ view-staff.php → update-status (reject) blacklist.php → add email (separate confirmation) staff-message → contact applicant * Architecture option: low-risk + zero flags → queue_status=dismissed without admin action (reduces noise). Configurable; default ON for tier=low only.

6.4 Review checklist (admin SOP)

  1. Open queue item → read flags and matched identities
  2. Compare staff profiles side-by-side (name, DOB, events, PSA)
  3. Check PSA compliance in Apply admin if psa_expired / psa_duplicate
  4. Decide: legitimate returning worker / family shared IBAN / likely duplicate account
  5. Mark OK, Escalate, or Dismiss with mandatory note if High risk
  6. Only if policy violation confirmed → use existing reject/blacklist flows manually

8. Risk score design

8.1 Score model

Integer 0–100, sum of triggered rules capped at 100. Computed once per successful submit. Immutable after write (new submit = new assessment).

Tiers

TierRangeQueue behaviour
Low0–25Auto-dismiss* or hidden from default filter
Medium26–60Open — appears in queue
High61–100Open — top sort; note required on review

Flag codes (canonical)

  • duplicate_pps duplicate_psa duplicate_iban duplicate_mobile
  • probable_same_person (name + DOB + different email)
  • disposable_email velocity_ip velocity_device
  • rapid_submit validation_burst
  • psa_expired psa_duplicate psa_images_missing
  • datacenter_ip (optional F4)

8.2 Rule weights (approved strategy)

Rule IDConditionPointsFlag
R01Normalised PPS matches different staff_id+35duplicate_pps
R02Normalised PSA matches different staff_id+30duplicate_psa
R03IBAN hash matches different staff_id+30duplicate_iban
R04E.164 mobile matches different staff_id+20duplicate_mobile
R05Same surname + first_name + DOB, different email+25probable_same_person
R06Email domain in disposable list+25disposable_email
R07>5 successful submits from IP in 24h+20velocity_ip
R08>3 distinct emails from device_hash in 7d+25velocity_device
R09Submit <60s after wizard start+10rapid_submit
R10≥3 validation failures in session before success+10validation_burst
R11PSA expiry date < today+15psa_expired
R12PSA images missing after submit+15psa_images_missing
R13Datacenter/VPN ASN (optional)+15datacenter_ip

Cap: risk_score = min(100, sum(points)). Tier from score. Multiple flags preserved in flags_json for admin transparency.
