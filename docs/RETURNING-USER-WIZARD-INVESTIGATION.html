Returning User Wizard — Production Investigation

Generated 6 June 2026 · Production: register.olasentra.com · Audit only — no code changes

Summary: Returning-user prefill works, but the wizard is still architected as an 8-step linear flow with no fast-track for complete profiles. Production issues (duplicate Continue + Submit, “None selected”, perceived jump to review) stem from nav chrome design, shift selection loss after email lookup, draft/resume bypasses, and missing returning-user short path — not from prefill failure. P0 shift-validation patches are in repo but do not deliver the 3-step experience users expect.

1. Reported production flow

Existing user enters email → Profile auto-loads correctly → User selects event → Wizard jumps to review / confirmation (perceived) → Continue + Submit Registration both visible → Continue not useful → User expects: Select event → Confirm profile → Submit (3 steps)

3. Root cause analysis

3.1 No fast-track path exists

Code review confirms no returning-user shortcut to a 3-step flow:

  • api/registrant-lookup.php returns profile_complete but wizard does not change step count.
  • registration-wizard-returning.js — prefill + welcome card; CTA “Pick new events” only calls showStep(2).
  • registration-wizard.js — fixed TOTAL = 8; navigation is always 1→2→…→8.
  • Complete profile users still traverse Steps 4–7 with validation gates — fields pass instantly because prefilled, which feels like a “jump” to review after event selection.

3.2 “None selected” on review

CauseMechanism
Shift cleared after email lookupStep 3 lookup → setRegisteredEventIds() → refreshShiftPicker() rebuilds cards; prior Step 2 selections for already-registered events become disabled and drop from :checked:not(:disabled).
Step 2 validation not re-rungoNext() validates only the active step. Once past Step 2, forward navigation does not re-check event_ids[] (P0 patch adds Step 8 + submit gate + lookup redirect — may not be on production cache yet).
Draft / resume bypassshowStep(n) without validation — resume prompt, REG_WIZARD_RESTORE_STEP, server error restore to Step 8.

3.3 Duplicate Continue + Submit Registration

Structural duplicate nav in markup:

index.php Step 8 panel:
  .form-actions--wizard-hidden  → hidden Submit (CSS)
registration-wizard-shell.php:
  #reg-wizard-nav              → Back + Continue/Review
  #reg-wizard-nav-submit        → Back + Submit

updateChrome() in registration-wizard.js should hide #reg-wizard-nav on Step 8 and show #reg-wizard-nav-submit when body.registration-page--wizard-review is set.

Duplicate buttons appear when:

  • current !== 8 but review panel visible (unlikely — same showStep controls both), OR
  • #reg-wizard-nav not hidden — stale JS, cached assets, or mainNav.hidden not applied, OR
  • User sees Continue from Step 7 (label “Review”) while Step 8 inline consent + hidden form-actions still affect layout on small viewports, OR
  • .reg-wizard__nav--submit has display:none until body review class — functional Submit hidden while a non-functional Continue remains visible.

3.4 “Jumps directly to review after selecting event”

Not a single automatic showStep(8) after event pick in code. Observed behaviour is explained by:

  1. Prefilled Steps 4–7 validate on first Continue click each — user advances quickly.
  2. Local draft resume may restore high step numbers.
  3. User mental model: email + event + confirm = done; 8-step chrome contradicts expectation.

8. Recommended solution (awaiting approval)

Phase A — UX defects (extends P0)

  1. Consolidate Step 8 nav to single source — remove duplicate .form-actions submit from wizard mode entirely.
  2. Ensure updateChrome() and CSS always toggle together; add defensive hidden on Continue when current === 8.
  3. Block showStep(8) without valid events (close draft bypass — P1 from prior report).

Phase B — Returning fast-track (new feature)

For profile_complete === true + PSA on file + lookup success:

  1. Step A — Your gigs (event selection, registered events greyed)
  2. Step B — Confirm profile (read-only summary: contact, payroll masks, PSA on file, consent)
  3. Step C — Submit

Implementation options:

  • Option 1 (recommended): Dynamic step map in wizard JS — 3 visible steps, internal validation unchanged.
  • Option 2: Keep 8 steps but auto-skip 4–7 with non-blocking banners (less clean UX).

Phase C — Verification

  • Production CDP script: returning complete profile → select open event → confirm ≤3 user actions to submit.
  • Screenshots: iPhone Safari, Android Chrome, desktop — review nav and selected events.
