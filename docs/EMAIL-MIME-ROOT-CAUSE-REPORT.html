Email MIME Root Cause Investigation

Generated 6 June 2026 · Based on docs/EMAIL-REJECTION-TEMPLATE-AUDIT.html · Investigation only — no code changes · Awaiting approval before implementation

Exact root cause: buildEmailMimePayload() in includes/mailer.php intentionally emits a single-part message. When $htmlBody is non-empty, it returns only text/html with quoted-printable encoding and never includes the $textBody argument. There is no multipart/alternative structure and no MIME boundary. Plain-text is built by every dual-format template but discarded at the MIME layer. Production defect symptoms (raw tags, split words, non-clickable URLs) occur when clients display the QP-encoded HTML part as plain text — not because boundaries are malformed (none exist).

1. Investigation questions — answers

#QuestionFinding
1Exact MIME structure currently generated?Single part. Either text/html; charset=UTF-8 + quoted-printable (when HTML provided) OR text/plain; charset=UTF-8 + 8bit (plain only). Never multipart.
2Why is plain-text missing?buildEmailMimePayload() lines 28–34: if ($html !== '') { return html only; } — $textBody parameter is ignored. Intentional per comment: “avoids raw multipart on mobile.”
3SMTP vs PHP mail() difference?Identical MIME body. Both call same buildEmailMimePayload($body, $htmlBody). SMTP adds Date/To/Subject/Message-ID headers; mail() passes subject separately and fewer headers. Content-Type, CTE, and body bytes are the same.
4QP soft breaks from bad boundaries?No. No multipart/* boundaries exist. Soft breaks are standard quoted_printable_encode() line wrapping at 76 octets (=\r\n). Defect appears when QP HTML is shown undecoded as text — missing text/plain alternative removes the safe fallback.
5Template impact?See §5. HTML+dual-format emails affected; plain-only emails unaffected.

Source evidence — intentional single-part design

includes/mailer.php lines 21–41:

/**
 * Build a single-part MIME body (HTML when available — avoids raw multipart on mobile).
 */
function buildEmailMimePayload(string $textBody, ?string $htmlBody): array
{
    $html = $htmlBody !== null ? trim($htmlBody) : '';
    if ($html !== '') {
        return [
            'content_type'      => 'text/html; charset=UTF-8',
            'transfer_encoding' => 'quoted-printable',
            'body'              => quoted_printable_encode(normalizeEmailLines($html)),
        ];
    }
    return [ /* plain only */ ];
}

8. Safe fix strategy (pending approval)

Recommended approach — single-file MIME fix

  1. Scope: Modify only buildEmailMimePayload() in includes/mailer.php (and add a small private helper for multipart assembly if needed).
  2. When both plain and HTML non-empty: Emit multipart/alternative with unique boundary (e.g. =_Olasentra_ + random hex).
  3. Part order: text/plain first, text/html second (RFC 2046 — plainer part first for clients that show multipart as text).
  4. Encodings: Plain: 8bit (UTF-8, normalized LF). HTML: keep quoted-printable or switch to 8bit on SMTP UTF-8 paths (either acceptable; QP is not the bug — missing plain part is).
  5. When HTML empty: Keep current plain-only path unchanged.
  6. When HTML only (edge case): Rare in this codebase; could fall back to HTML-only or synthesize plain via strip_tags — prefer requiring callers to pass plain (all current callers already do).
  7. Do not change: Template functions, subjects, copy, SMTP socket logic, admin triggers.
  8. Verify: Extend scripts/audit-email-mime-structure.php to assert multipart; re-run scripts/audit-rejection-email-mime.php; production send via cron/email-production-verify.php; manual Gmail/Outlook plain-text + HTML view.
  9. Deploy: includes/mailer.php only via deploy.ps1 (already in FTP manifest).

Alternative considered — HTML 8bit without multipart

Rejected as primary fix: switching HTML to 8bit without adding text/plain would reduce QP artefact visibility but would not fix plain-text-only clients or security scanners that strip HTML. Does not meet RFC best practice.
