Anti-Fraud Protection Review

Olasentra Registration (register.olasentra.com) | Phase A.7 addendum | Generated 2026-06-06 | Review only — no enforcement implemented

Executive summary: The platform has solid baseline protections against the most common duplicate-application scenario (same email + same event) and blocks blacklisted staff. However, cross-identity fraud (same person, different email), device/session velocity, payroll detail sharing, and proactive PSA duplicate detection are largely unmonitored. Recommended approach: Shadow Mode — compute risk scores and queue flags for admin review without auto-rejecting applicants.
Production rule (approved for this review): Do not automatically reject applicants. Initial deployment must be Shadow Mode only — flag suspicious records for admin review. Live blocking requires separate approval after shadow metrics are validated.

Recommendations (shadow mode)

  • Add registration_fraud_signals table (or extend audit log) written on every successful submit.php save — never blocks submit in shadow mode.
  • Normalise and hash sensitive fields (PPS, IBAN last 4, PSA, mobile E.164) for lookup; store raw values only where already required for payroll.
  • Run duplicate queries: “another staff row exists with same normalised PPS / PSA / IBAN / mobile?” → flag duplicate_identity.
  • Composite match: same surname + first_name + date_of_birth with different email → flag probable_same_person.
  • Surface flags on admin Fraud Queue (Section 7) — status review_required, not rejected.

Implementation roadmap

No code from this roadmap should ship until this review is approved.

Phase F1 — Shadow foundation (2–3 days)
  • Add feature_fraud_shadow_mode flag (default OFF)
  • Migration: registration_fraud_signals + registration_submit_meta tables
  • Post-save hook in submit.php (after successful save only) — write IP, UA, session id
  • Duplicate queries for normalised PPS, PSA, IBAN, mobile
  • Compute score; insert signal row; never alter HTTP response
Phase F2 — Scoring & velocity (2–3 days)
  • Disposable email domain list (static JSON, weekly update)
  • Velocity counters (IP 24h, device 7d) in meta table or Redis/file cache
  • PSA expired + duplicate PSA flags
  • Cron fraud-velocity-scan.php + optional email alert
Phase F3 — Admin Fraud Queue (3–4 days)
  • admin/fraud-queue.php list + detail drawer
  • Filters: duplicates, compliance, suspicious, review required
  • Audit log on review actions
  • Sidebar link under Staff section
Phase F4 — Hardening (optional)
  • Lightweight client fingerprint (privacy assessment)
  • IP intelligence API for datacenter/VPN ASN (shadow flag only)
  • Enable shadow mode on staging → production soak 2 weeks
  • Metrics review before any live block discussion
Phase F5 — Live enforcement (future, separate approval)
  • feature_fraud_shadow_mode = 2 — block only highest-confidence duplicates (e.g. same PPS + same PSA + different email)
  • Requires legal sign-off, false-positive analysis from shadow period, and rollback plan
