# v1.1 Extension Guide

How to add functionality without modifying v1.0 core modules.

---

## Principles

1. **Hook, don't fork** — call existing helpers (`getStaffAuthPolicy()`, `getSetting()`, `recordCheckin()`).
2. **Feature-flag new behaviour** — use `includes/feature-flags.php` and admin settings.
3. **One deploy bundle** — add new files to `scripts/upload-safe-fix-bundle.ps1` or a feature-specific upload script.
4. **JSON APIs** — wrap in try/catch; never expose stack traces.

---

## Suggested layout

```
modules/
  library/
    LibraryModule.php      # bootstrap: register routes, admin menu
    admin/
      index.php            # thin admin page — includes auth + layout
    api/
      books.php            # optional JSON endpoint
    includes/
      library-repository.php

features/
  studio-booking/
    README.md
    ...

integrations/
  external-crm/
    webhook-handler.php
```

---

## Admin page pattern

```php
<?php
declare(strict_types=1);

require_once dirname(__DIR__, 2) . '/config.php';
require_once dirname(__DIR__, 2) . '/includes/admin/auth.php';
requireAdmin();

// Load module code only — do not duplicate auth logic
require_once __DIR__ . '/../includes/library-repository.php';

// Render using existing admin layout includes
```

Register menu items via a single admin hook file (future) or document the manual `admin/` link in the module README.

---

## API pattern

```php
<?php
declare(strict_types=1);

header('Content-Type: application/json; charset=utf-8');

require_once dirname(__DIR__, 2) . '/config.php';

try {
    // Use existing mobile auth or portal session helpers
    $pdo = getDB();
    // ...
    echo json_encode(['ok' => true, 'data' => $result]);
} catch (Throwable $e) {
    error_log('[EventStaff] module/library: ' . $e->getMessage());
    http_response_code(500);
    echo json_encode(['ok' => false, 'error' => 'Service unavailable']);
}
```

For mobile-facing endpoints, prefer extending `includes/mobile/mobile-router.php` with new routes under `/api/mobile/v1/` — **additive fields only** within v1.

---

## Mobile config extensions

Add optional keys to `MobileConfigService` response only when the feature is enabled:

```php
if (isFeatureEnabled($pdo, 'feature_library_module')) {
    $config['library'] = ['enabled' => true, 'url' => '...'];
}
```

Never remove or rename existing config keys in v1.1.

---

## Database changes

- New tables/columns: ship SQL migration in `database/migrations/` with idempotent `CREATE TABLE IF NOT EXISTS`.
- **Never drop** v1.0 tables or columns in v1.1.
- Run migrations via documented cron or admin one-shot script.

---

## Health checks

Add an isolated check in `includes/admin/system-health.php`:

```php
// Example pattern — one failure must not crash the page
try {
    $checks[] = runLibraryModuleHealthCheck($pdo);
} catch (Throwable $e) {
    $checks[] = ['id' => 'library', 'status' => 'fail', 'message' => 'Check error'];
}
```

---

## Deployment

1. Add all new paths to `scripts/upload-safe-fix-bundle.ps1` (or `scripts/upload-feature-<name>.ps1`).
2. Update `scripts/deploy-ui-api-manifest.json` bundle entry.
3. Bump `storage/version.json` on production deploy.
4. Run post-deploy verification from `docs/V1.1-DEVELOPMENT-BASELINE.md`.

---

## What not to do in v1.1

- Rename public routes or API paths
- Change `getStaffAuthPolicy()` contract
- Replace `recordCheckin()` with parallel logic
- Remove legacy session keys or mobile config fields
- Deploy without manifest update
