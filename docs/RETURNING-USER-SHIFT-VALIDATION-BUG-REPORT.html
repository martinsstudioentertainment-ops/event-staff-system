Returning User Shift Validation Bug — Root Cause Report

Generated 6 June 2026 · Production: register.olasentra.com/index.php · Wizard flag feature_registration_wizard_v2 ON · Investigation only — no code changes

Production defect confirmed (architecture). Returning users can reach Step 8 (Review) with zero selectable shifts, see “None selected” in the review summary, encounter duplicate navigation buttons, and be unable to complete submission. Root cause is not a regression of the Step 2 pointer-events lock (fixed 6 June). It is a validation gap: Step 2 event selection is enforced only when leaving Step 2; later steps and direct showStep() jumps do not re-check event_ids[]. Returning-user email lookup on Step 3 can clear or invalidate prior shift selections via refreshShiftPicker(), after which the wizard still allows forward navigation to Review.

1. Reported production flow

Email found ↓ Profile auto-filled ↓ Wizard still carries all 8 steps ↓ Review page ↓ Buttons duplicated (Continue + Submit registration) ↓ No shift selected (“Selected Opportunities → None selected”) ↓ Submit registration not clickable

Autosave re-collects only enabled checked inputs.

Failure to toggle either leaves Continue visible and/or Submit non-functional (CSS display:none on .reg-wizard__nav--submit).

3. Root cause chain

3.1 Primary: Step 2 validation is single-shot

registration-wizard.js — goNext()
  validateCurrentStep()   // only validates `current` step
  showStep(current + 1)   // no retroactive checks

registration-wizard-validation.js — validateStep(8)
  checks privacy_consent ONLY
  does NOT check event_ids[]

Once a user leaves Step 2 (by Continue or by showStep(n) jump), nothing in the forward path re-validates shift selection before Review or submit. Step 8 submit handler also calls validateStep(8) only — consent gate, not shifts.

3.2 Returning-user trigger: picker rebuild clears selection

Step 3 email blur/input
  → registration-wizard-returning.js lookupEmail()
  → smartPrefill() → setRegisteredEventIds(registered_event_ids)
  → events.js refreshShiftPicker()
  → populateWizardEventCards() — innerHTML rebuild
  → applyRestoredEventSelection() — only checks :not(:disabled)
  → persistShiftSelection() — dataset.selected may become []

Before lookup on Step 3, REGISTERED_EVENT_IDS is empty; all cards appear open. User may select shifts on Step 2, pass validation, then lose those selections when lookup marks prior events as registered/disabled. Forward navigation from Steps 3–7 does not detect the loss.

6. Reproduction scenarios (for fix verification)

  1. Selection loss after lookup: Step 1 → Step 2 → select an event → Continue → Step 3 enter returning email already registered for that event (or only registered events remain) → Continue through Steps 4–7 → Review. Expect: “None selected”, Step 2 validation would fail if re-run.
  2. Draft resume bypass: Start wizard, reach Step 4+ without selecting shifts (or after selection cleared), save draft, resume → jump to Step 7/8 via resume prompt. Expect: review reachable without Step 2 validation.
  3. Review chrome: On Step 8, inspect #reg-wizard-nav (should be hidden), #reg-wizard-nav-submit (should be flex), body.registration-page--wizard-review (should be present). Expect for defect: Continue visible and/or Submit nav display:none.
