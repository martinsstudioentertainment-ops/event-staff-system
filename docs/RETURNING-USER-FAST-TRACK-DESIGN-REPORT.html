Returning User Fast-Track — Implementation Design Report

Generated 7 June 2026 · Production: register.olasentra.com · Planning only — no implementation in this deliverable

Executive summary: A partial fast-track is already deployed behind feature_registration_wizard_v2, but it does not match the approved 3-step target (events → confirm profile → submit). Complete-profile users still pass through Welcome and Email before shift pick, with consent on the shift step and no dedicated masked profile summary. Several P0 UX defects (duplicate nav, “None selected”) are largely addressed in code; the remaining work is a fast-track v2 step remap plus hardening of event persistence and autosave/restore paths. No server schema changes required.

2. Current architecture (as implemented)

index.php data-step order in markup:

  4 About you

2.2 Fast-track activation

  • api/registrant-lookup.php returns profile_complete via staffNeedsProfileForm().
  • registration-wizard-returning.js calls RegistrationWizard.setFastTrack(true) when complete; auto-advances from step 3 → step 2 after email lookup.
  • registration-wizard.js uses FAST_TRACK_LABELS remap and skips steps 4–7; submit on physical step 2.
  • Consent checkbox is moved into #reg-fast-track-consent-mount on the shift step.
  • No pickable shifts → Return to home instead of Submit (recent addition).

2.3 Server submit path

  • submit.php loads $existingStaff by email; PSA validation and registrationFormReadyForShiftSelection() accept on-file PSA images from staff row.
  • Hidden prefilled fields (PPS, IBAN, address, etc.) are posted even when steps 4–7 are skipped — server already supports fast-track submit without UI traversal.
  • Duplicate event IDs filtered server-side; all-duplicate selection returns error + status redirect.

3. Target fast-track design (recommended v2)

GATE (compact, not counted in user-facing 3 steps) Role + email on Welcome OR dedicated email micro-step → registrant-lookup → if profile_complete: enter FAST_TRACK_V2 FAST_TRACK_V2 Step 1 — Select event(s) [physical step 2] Shift picker only; email shown read-only chip Continue requires ≥1 pickable selected shift FAST_TRACK_V2 Step 2 — Confirm profile [new summary panel; physical step 8 shell OR inline on step 2] Name, mobile, address (not full re-entry) PSA status badge (on file / expiring / missing) PPS + IBAN masked (reuse maskPps / maskIban from review.js) Privacy consent checkbox Continue → Step 3 FAST_TRACK_V2 Step 3 — Submit [same panel or lightweight confirm] Back + Submit registration only No Continue button

3.1 Why keep a hidden “gate” before events?

Returning detection requires email before registered_event_ids can grey out cards. The approved UX puts events first visually, but email must be resolved first. Recommended compromise: after role selection, collect email on Welcome (single field) → immediate lookup → if complete, first user-facing fast-track screen is events (user perceives 3 steps, not Welcome+Email+Events).

3.2 Profile summary panel (new)

  • Add renderFastTrackProfileSummary() in registration-wizard-review.js (mask helpers already exist).
  • Prefer server-provided masked payroll in lookup API (masked_pps, masked_iban) so raw values are not re-exposed in DOM for returning users.
  • Include link: “Update profile” → staff-profile.php (explicit opt-in; no inline edit in wizard).
  • Move consent from shift footer to summary step (requirement #1).

5.2 Architectural concerns (review before coding)

  • Email vs events ordering: True “events first” without any email gate is impossible without weakening duplicate-registration protection. Mitigation: one-field email on Welcome, then user-visible fast-track starts at events.
  • Dual step maps: Maintaining 8-step full wizard + fast-track v2 remap increases complexity. Mitigation: centralise step routing in registration-wizard.js with explicit FLOW_FULL / FLOW_FAST_V2 tables.
  • Security of masked fields: Client-side masking is display-only; server must not echo full PPS/IBAN in lookup JSON for returning users if summary is shown before submit.
  • Profile rollout flag: staff_profile_update_required may force incomplete state even when user believes profile complete — fast-track must respect staffNeedsProfileForm() (already does).

7. Rollback plan

  1. Immediate (no deploy): Disable wizard flag via admin/feature-flags.php or cron/wizard-flag-toggle.php → legacy non-wizard form.
  2. Fast-track only: In registration-wizard-returning.js, force setFastTrack(false) for all users (one-line hotfix) — restores full 8-step for everyone while keeping wizard v2 shell.
  3. Full revert: Git revert commits touching wizard JS/CSS/shell; redeploy via deploy.ps1; purge CDN/browser cache.
  4. Data: No DB rollback needed — changes are client flow only.
  5. Verification after rollback: New user completes 8 steps; returning user can still register via full wizard; submit.php acceptance unchanged.

8. Recommended implementation approach

Phase A — Align fast-track with approved 3-step UX (P0)

  1. Refactor fast-track step map to user-facing: Events → Confirm → Submit.
  2. Implement profile summary panel with masked payroll and PSA status badge.
  3. Move consent to confirm step; Submit only on step 3.
  4. Keep Welcome+email as pre-fast-track gate (single screen, not counted in progress).

Phase B — Hardening (P1)

  1. Defer shift picker initialisation until after successful lookup OR rebuild selection from dataset.selected after refreshShiftPicker.
  2. Block autosave restore to step 8 when isFastTrack().
  3. Add server-masked fields to lookup API.
  4. Update automated verification scripts.

Phase C — Deploy & monitor

  1. Deploy behind existing feature_registration_wizard_v2 (already on production).
  2. Watch registration-analytics for returning_fast_track, drop-off at new step 2, duplicate_application_prevented.
  3. Hard-refresh guidance for testers after FTP deploy.

9. Decision

Proceed with implementation? Yes — no blocking architectural concerns, but do not treat current fast-track as complete. Implement as fast-track v2 step remap per Section 3. Estimated touch: ~10 files, client-side only, low server risk. Recommend Phase A first, then Phase B hardening before marketing the flow to returning users.
